# zudedup — Roadmap to 0.1.0 (first CRAN release)

Companion to [design.md](design.md). Section references (§) point there.

**Status:** adopted 2026-10-08 from [RFC 0006](https://github.com/pedrobtz/packages/blob/main/rfcs/0006-zudedup-content-defined-chunking.md). Each stage's **Status:** line says where it stands.

## Sequencing principles

1. **The format constants land first and never move.** The gear table, the mask placement and the boundary fixture are Stage 0's deliverable, because every later stage, and every store a user ever writes, depends on them not changing (§6).
2. **The chunker is proven block-independent before anything consumes it.** The property test and the fuzzer land with the chunker (Stage 1), not after the store exists.
3. **Hashing and manifests before the store.** The store is R code over a backend; the backend is a contract other packages hold (§9), so it is written against a manifest type that already exists.
4. **Every stage ends with something runnable and tested.**
5. **A stage is done when its exit criteria pass in CI on all three platforms**, not when the code is written.
6. **Gates need canaries.** A fuzz target is trusted once `fuzz_canary` has crashed; a guard once its mutation case has been seen to pass without it.
7. **Change the design in the same commit as the contract.**

Sizes are relative: **S** ≈ a sitting, **M** ≈ a few, **L** ≈ the stage is the week.

**Status never goes in a heading.** A heading is `## Stage N — Title · Size` and nothing else; the state is the **Status:** line under it.

**Tracking.** A `v0.1.0` parent issue and one `stage`-labelled sub-issue per stage, each linking to its heading here. None exists on 2026-10-08; Stage 0 opens them and `.github/scripts/stage-cards.sh` in `pedrobtz/packages` puts the parent on the board. Each stage gains a **What actually happened** block when it closes.

## The release order, and what it costs

zudedup's C includes `zufast`'s `hash.h`, so `LinkingTo: zufast (>= 0.1.0)` is unconditional and **zufast must be on CRAN before zudedup can be submitted** (alignment R10.2). On 2026-10-08 zufast is tagged 0.1.0 and not on CRAN. Until it is, `DESCRIPTION` carries `Remotes: pedrobtz/zufast@main`, and Stage 6 removes the field and rebuilds against the CRAN tarball (R10.3). Every stage before 6 can proceed.

`zucrypt` is a `Suggests`, but it is not on CRAN either (*verified 2026-10-08*), and a `Suggests` outside the mainstream repositories is a NOTE at submission: before Stage 6, zucrypt is on CRAN or `Additional_repositories` names where it is. Until then it is in `Remotes:` with zufast. `dastash` waits on zudedup, not the other way round.

## Working rhythm

One pull request per stage: branch `stage-N-<slug>` from `main`; `devtools::document()`, `devtools::test()`, `devtools::test(shuffle = TRUE)` and `devtools::check(cran = TRUE)` clean at 0/0/0 locally before pushing; the PR body states the stage and its exit criteria as a checklist, carries `Closes #<n>` for the stage issue and the `full-ci` label; every CI leg green before merging; then update `.claude/CLAUDE.md`'s current-state paragraph and the **Status:** line.

Local traps the siblings hit: roxygen2 must be 8.1.0 or newer or `document()` rewrites `man/`; `devtools::check()` offline NOTEs on the system clock, silenced with `_R_CHECK_SYSTEM_CLOCK_=0`.

## Testing strategy, fixed once

- Self-sufficient tests: inputs built inside each `test_that()`, byte-explicit where bytes matter, `withr::local_seed()` for anything random, everything written under a `withr::local_tempdir()`.
- Assert on condition classes and fields (`hash`, `index`, `limit`), never message text.
- Serial testthat, no `Config/testthat/parallel`; `devtools::test(shuffle = TRUE)` in every definition of done; shared code only in `helper-*.R`.
- Helpers: `helper-bytes.R` (`splitmix_bytes(n, seed)`, the documented generator behind every fixture; `bytes()` from hex), `helper-expect.R` (`expect_chunks(x, table)`, `expect_zudedup_error(expr, class, ...)`), `helper-store.R` (`local_store()` over a temp directory; `corrupt_chunk()`), `helper-skip.R` (`skip_heavy()` on `ZUDEDUP_SKIP_HEAVY`, set by the gctorture and valgrind legs; `skip_if_no_slow_tests()` on `ZUDEDUP_SLOW_TESTS`; `skip_if_not_installed("zucrypt")`, `skip_if_not_installed("callr")`).
- Fixtures: `tests/testthat/fixtures/boundaries.tsv` (the format gate), small files for the store tests, `hash-reference.tsv` with digests pinned once from libxxhash and hashlib (Stage 2); read with `colClasses = "character"`; never regenerated by a test.
- CRAN budget: under 15 s; the 100 MB distribution and dedup properties behind `skip_heavy()`, run in CI.

## Stage 0 — Package identity, the gear table, the boundary fixture · S

**Status:** done 2026-10-08 ([#2](https://github.com/pedrobtz/zudedup/issues/2)).

**Goal:** the `usethis` skeleton becomes a package that checks 0/0/0, and the format constants exist with the means to regenerate and compare them.

**Do**

- `DESCRIPTION`: `Title: Content-Defined Chunking and Content-Addressed Storage`; a `Description` naming FastCDC, XXH3-128, manifests and the store; `Authors@R` Pedro Baltazar (`aut`, `cre`, `cph`); `Depends: R (>= 4.1)`; `LinkingTo: zufast (>= 0.1.0)`; `Remotes: pedrobtz/zufast@main` (development only); `Imports: jsonlite`; `Suggests: zucrypt, dastash, callr, testthat (>= 3.0.0), withr, knitr, rmarkdown`; `VignetteBuilder: knitr`; `Language: en-GB`; `Config/roxygen2/version: 8.1.0`; `URL`, `BugReports`; `Config/testthat/edition: 3`, no `parallel`. No `Copyright:`: nothing is vendored.
- `LICENSE`, `LICENSE.md` with the real holder.
- `.Rbuildignore`: `^\.agents$`, `^\.claude$` (added with these documents), `^tools$`, `^fuzz$`, `^cran-comments\.md$`, `^CRAN-SUBMISSION$`, object patterns; the same object patterns in `.gitignore`.
- `src/init.c` registering an empty table with `R_useDynamicSymbols(dll, FALSE)` and `R_forceSymbols(dll, TRUE)`; delete `src/zudedup.c`; `src/Makevars` with `PKG_CFLAGS = $(C_VISIBILITY)` and hand-listed `OBJECTS`.
- `R/conditions.R` with the §11 hierarchy and `?"zudedup-conditions"`; `NEWS.md` `# zudedup 0.0.0.9000`; `tests/testthat/test-init.R` written before the template test is removed.
- **The gear table.** `tools/make-gear.R`: SplitMix64 from seed `0x5A5A5A5A5A5A5A5A`, 256 values, written to `src/zdd_gear.h` with the seed, the script's path and the date in its header comment; a test regenerates the table from the seed in R and compares.
- **Decide §18 Q4** (mask placement) by chunking the fixture input with both placements in a scratch R implementation and comparing size distributions; record the choice and its two masks for 8 KiB in `zdd_gear.h` and design §6.2.
- **The fixture input.** `helper-bytes.R`'s `splitmix_bytes(4 * 1024^2, seed)` with a documented seed; the boundaries themselves are committed at Stage 1, when the chunker exists.
- **Decide §18 Q5**: search the CRAN index for content-defined chunking and record the result in design §3.2.
- Verify `zdd_` is free against every sibling's `src/` and `inst/include/`.
- `coverage.yaml` pinned by commit; `.github/dependabot.yml`; `_pkgdown.yml` with `development: mode: auto`.
- `.claude/CLAUDE.md`: update the current-state paragraph.
- Open the tracking issues; create the `stage` and `full-ci` labels.

**Exit**

- `devtools::check(cran = TRUE)` 0/0/0 locally with zufast installed; `R-CMD-check.yaml` green on every leg.
- `src/zdd_gear.h` committed, regenerable, with the mask placement decided and recorded.
- The tracking issues exist and the parent is on the board.

**Not this stage:** any chunking code.

**What actually happened**

- §18 Q4 was decided by reading the Python `fastcdc` 1.7.0 source rather than by a scratch R implementation: its rule is a right-shift gear hash with contiguous low-bit masks, which is sound for low bits (a left shift is not), and a 4 MiB measurement showed its normal point (`avg - 1.5 min`) puts the mean near `avg` where a switch at `avg` gives about 10 KiB. The whole rule became D14; the table entries are shifted right one bit (D19) so Python's unbounded integers and C's `uint64_t` agree. The review before the stage also settled D15–D18.
- The gear table is checked through an internal `.Call` (`zudedup_gear_table`) against the R regeneration, since `src/` is not reachable from the tests under `R CMD check`.
- `$(C_VISIBILITY)` hides `R_init_zudedup` too unless it is marked `attribute_visible`; without that, R silently skips registration.
- `Imports: jsonlite` moves to Stage 3: declared but unused it is a NOTE. `dastash` left `Suggests`. zucrypt is not on CRAN, so it joined zufast in `Remotes:` and became a Stage 6 item.
- The parent issue is #1, the stages #2–#8. Adding zudedup to `stage-cards.sh` in `pedrobtz/packages` (the board) is left to the maintainer.

## Stage 1 — The chunker, block independence, fuzzing · M

**Status:** done 2026-10-08 ([#3](https://github.com/pedrobtz/zudedup/issues/3)).

**Goal:** `dedup_chunk()` returns the same chunk table for the same bytes however they arrive, and the boundary fixture is committed.

**Do**

- `src/zdd_check.h` (the R-free interface), `src/zdd_cdc.c`: the gear hash, normalised chunking with the two masks, `min` and `max` enforcement, `zdd_cdc_feed()` carrying state across blocks, the state struct serialised to and from a raw vector.
- `.Call` entry points: `zudedup_cdc_init(min, avg, max)` → state; `zudedup_cdc_feed(state, block)` → boundaries within the block and the new state; `zudedup_cdc_finish(state)` → the last chunk. Argument validation in `R/args.R`: `avg` a power of two in `[min, max]`.
- `R/chunk.R`: `dedup_chunk()` over a raw vector (one feed) or a connection (1 MiB blocks through `readBin()`); the table of `offset`, `length` and, from Stage 2, `hash`.
- `tests/testthat/fixtures/boundaries.tsv` committed from the fixture input; `test-boundaries.R` reproduces it.
- `test-block-independence.R`: every fixture in block sizes 1, 7, 4096, 65536 and 1 MiB, and whole.
- `test-distribution.R`: 100 MB of random bytes, bounds and mean (behind `skip_heavy()`).
- `fuzz/fuzz_cdc.c` under `-DZDD_STANDALONE`: splits its input at random points, feeds both ways, traps on a boundary difference; `fuzz/fuzz_canary.c`; `tools/run-fuzz` requiring the canary to crash first; `hardening.yaml`.
- `tools/run-lint`, `tools/check-symbols` (each seen to fail on a plant); `native-checks.yaml`.

**Exit**

- `boundaries.tsv` reproduces on every CI platform; block independence holds for every fixture and under the fuzzer for the PR budget; the canary has crashed.
- No chunk under `min`, none over `max` except the last, mean within 10 % of `avg`.
- Sanitizers, valgrind, rchk and gctorture clean.

**What actually happened**

- The fixture boundaries were checked against Python `fastcdc` 1.7.0 (`fastcdc_py.fastcdc_py()` with `GEAR` replaced) before they were committed: 494 chunks at the defaults and 16,135 at the smallest parameters (64, 256, 1024), identical. Both tables are committed (`boundaries.tsv`, `boundaries-small.tsv`); the small one exercises thirty times as many cuts.
- `dedup_chunk()` also takes a path, through `R/zu_source.R`, copied from zuxml here rather than at Stage 2.
- Block size 1 runs over a 150 KB prefix of the fixture, not all 4 MiB (four million `.Call`s); the fuzzer covers arbitrary splits.
- The fuzz canary is the same harness with a real block-independence bug compiled in (the hash forgotten at each block edge), so its crash proves the comparison detects the fault it exists for.
- `tools/check-symbols` also checks that `R_init_zudedup` is the only exported symbol, and proves both checks against a planted object.

## Stage 2 — Hashing and manifests · S

**Status:** done 2026-10-08 ([#4](https://github.com/pedrobtz/zudedup/issues/4)).

**Do**

- `zuf_hash128()` per chunk and `zuf_hasher_*` streamed over the object, in the feed loop, so bytes are read once; the §7 rendering (`high` then `low`, lower-case hex).
- `hash = "sha256"`: `zucrypt::crypt_hash()` per chunk and over the object, from R; `zudedup_invalid_argument` naming `zucrypt` when it is not installed.
- `R/manifest.R`: `dedup_manifest()` over raw, connection or path (through `R/zu_source.R`, copied verbatim from `../zuxml`); the `dedup_manifest` class with `print`, `format`, `as.data.frame`, `length`; `R/validate.R` validating a manifest whole (§12: hex of the right length, lengths in range, sum equals `size`, `max_chunks`).
- `tests/testthat/fixtures/xxh3-reference.tsv`: digests of the fixtures pinned from `xxhsum`'s 128-bit mode, once; `test-hash.R` compares, and compares SHA-256 against `openssl` when zucrypt is installed.
- `zudedup_info()`: zufast version compiled against, the gear table's seed, the mask placement, the defaults.

**Exit**

- Every fixture's XXH3-128 matches the pinned `xxhsum` output; the whole-object digest equals `zufast::fast_hash()` of the object.
- Every manifest validation guard has a test with a crafted manifest.

**What actually happened**

- No `xxhsum` was at hand, so the reference digests (`fixtures/hash-reference.tsv`, one file for both algorithms) were pinned from libxxhash 0.8.3 through python-xxhash 4.0.1 (`xxh3_128().hexdigest()`, the text `xxhsum -H2` prints) and from Python's `hashlib` for SHA-256: fifteen whole inputs straddling XXH3's internal size thresholds, the fixture, and the fixture's 494 chunks. Stage 5's conformance job re-checks them against `xxhsum` itself.
- `dedup_chunk()` gained `hash =`, so the chunk table and the manifest offer the same two algorithms; the design's §5 signature records it.
- The chunk digest is computed in the feed loop: one-shot `zuf_hash128()` for a chunk that lies inside one block, the carried `zuf_hasher` for one that spans blocks. Both hashers sit in the state vector and are copied through an aligned local each call (§13).
- SHA-256 works as D15 says: chunk digests always; the object digest from a raw vector or by re-reading a path; `NA` for any other connection.
- `zufast` joined `Suggests` (it is already `LinkingTo`) so a test can compare the object digest with `zufast::fast_hash()`.
- The R-side manifest guards carry `# GUARD: name` markers and a `test_that("GUARD name")` each, for Stage 3's mutation check.

## Stage 3 — The filesystem store and the backend interface · M

**Status:** done 2026-10-08 ([#5](https://github.com/pedrobtz/zudedup/issues/5)).

**Do**

- `R/backend.R`: `dedup_backend()` validating the five functions' presence and arity; the filesystem backend as its first instance.
- `R/store.R`: `dedup_store(path, create)`, `zudedup.json` (algorithm, params, format version 1) written at creation and checked at every open; `dedup_put()` (chunk, hash, one `has()` call, write missing to `tmp/`, rename), `dedup_get()` (verify per chunk; to memory under `max_size`, or streamed to `file`), `dedup_has()`, `dedup_missing()`, `dedup_delete()`.
- `zudedup_store_error` with `hash` and `index`; `zudedup_algorithm_error` on a mismatched manifest.
- Guards marked for `tools/run-mutation-check`, which lands here.
- Tests over `local_store()`: round trips, a corrupted chunk refused on get, a manifest with the wrong algorithm refused, `dedup_missing()` before and after a put, a backend missing `delete`.

**Exit**

- Every §8 behaviour has a test; `tools/run-mutation-check` passes and has been seen to fail.
- A `dedup_backend()` built from five closures over an environment passes the same tests as the filesystem store (the interface is proven by a second instance).

**What actually happened**

- `tools/run-mutation-check` is R (`tools/mutation-check.R`): it parses each file, replaces the condition of every `# GUARD:` `if` with `FALSE` in the namespace `pkgload` loaded, and runs the one test named `GUARD name` (testthat's `desc =`), which must pass first and fail after. On its first run it failed on five guards, so it has been seen to fail: `chunk-missing` (the length check raised the same class), which led to the `problem` field (`"missing"` or `"corrupt"`) on `zudedup_store_error`; `fields`, `params` and `hashes-type`, which later guards subsume and which are now plain checks; and `chunk-oversize`, which saves memory but changes no outcome and is now documented defence in depth. Seventeen guards are load-bearing.
- `dedup_store()` takes `hash`, `min`, `avg` and `max` for a new store; an existing store keeps its own, and only the settings a call gives are compared with them (by value, so `256L` matches 256).
- `dedup_put()` has no `...`: the store fixes every chunking setting. `has()` answers are checked for shape (`has-shape`), since a wrong answer would skip chunks never written.
- `jsonlite` joined `Imports` here, with its first use.
- Every store test runs over both kinds through `local_store(kind)`.

## Stage 4 — Diff, gc, verify; the concurrency tests · S

**Status:** done 2026-10-08 ([#6](https://github.com/pedrobtz/zudedup/issues/6)).

**Do**

- `dedup_diff()` (§10), `dedup_verify()`, `dedup_gc(store, keep)` including `tmp/` cleanup.
- `test-concurrency.R`: two `callr` processes `dedup_put()` the same object into one store; one copy results, both manifests equal. A leftover `tmp/` file is removed by `dedup_gc()`.
- The dedup property: a 10 MB object with 1 % of bytes changed at 100 points shares at least 95 % by `dedup_diff()` (behind `skip_heavy()`).

**Exit**

- Every function of §5 exists and is tested; the two-process test passes on all three platforms.

**What actually happened**

- The dedup property's 95 % was arithmetic, not measurement: with 8 KiB chunks each of 100 scattered edits costs about one size-biased chunk (about 11 KB), so about 89 % is shared, measured 0.889–0.896. The test asserts 85 % and design §15 says why.
- `dedup_verify()` returns the corrupt digests (empty when sound) rather than a flag, so a caller can delete or re-fetch them.
- `dedup_gc()` accepts one manifest or a list, and empties `tmp/` only for a filesystem store; a backend's own partial writes are its business (D16 makes them its responsibility).
- The two-process test runs each put in a `callr` background process; under `devtools::test()` the process loads the source with `pkgload`, under `R CMD check` the installed package. It is behind `skip_heavy()`, so it runs in CI's full profile and locally, not on CRAN.
- `fixture_bytes()` is cached in the helper: generating 4 MiB of SplitMix64 in R is cheap natively and slow under valgrind, where Stage 1's PR spent most of its time.
- CI taught three things. The two-process test's first Windows run outlasted a two-minute wait at eight thousand chunk files per writer; it now uses about a thousand and waits ten minutes. Valgrind, run long enough by the heavy tests, reported one possibly-lost block from cli's timer thread, suppressed by path in `tools/valgrind.supp`. And at Stage 2 gctorture timed out at two hours on R arithmetic over the 4 MiB fixture; `skip_under_torture()` skips the fixture-scale tests under `ZUDEDUP_SKIP_HEAVY`, which CRAN and the other legs still run, and the job's timeout is 240 minutes.

## Stage 5 — Conformance against Python `fastcdc`; benchmarks; docs · M

**Status:** done 2026-10-08 ([#7](https://github.com/pedrobtz/zudedup/issues/7)).

**Do**

- `tools/run-conformance`: installs the Python `fastcdc` package in a virtual environment, substitutes zudedup's gear table (and masks, if §18 Q4 chose the spread placement), chunks every fixture, compares with `dedup_chunk()`; `conformance.yaml` runs it on Linux; nothing under `tests/` needs Python.
- `tools/run-benchmarks`: chunking throughput, hashing, `dedup_put()` of 1 GB against `writeBin()`; results recorded in design §16.
- Documentation: every export with `@return` and runnable `@examples`; `?"zudedup-conditions"`; a vignette, *Versioning large objects with zudedup* (two versions of a data frame, the shared fraction, a store, a diff); `_pkgdown.yml` listing every export; README rewritten; `inst/WORDLIST`; `cran-comments.md` listing the CI legs.
- **Decide §18 Q1 to Q3**, record in §17.

**Exit**

- Python `fastcdc` agrees on every fixture in CI; benchmarks recorded; `devtools::check(cran = TRUE)` 0/0/0; `pkgdown::check_pkgdown()` clean.

**What actually happened**

- `tools/run-conformance` compares 16 inputs (the fixture, every file under `fixtures/`, SplitMix64 streams of awkward sizes, zeros, a repeating pattern and CSV text) at 7 parameter sets with Python `fastcdc` 1.7.0, and every input and every fixture chunk with `xxhsum -H2`. `fastcdc_py.fastcdc_py()` runs unchanged with only `GEAR` replaced (D14). Locally all 112 boundary comparisons agreed; the `xxhsum` half runs in CI, where apt provides it.
- The put target of §16 is not met and cannot be by a one-file-per-chunk store: 44× `writeBin()`, 213 µs per chunk written, almost all of it file creation and rename. §16 records the measurement and why; the chunking target (1 GB/s) is met at 1.46 GB/s. The benchmark's first version timed a promise once and reported infinite throughput; it now re-evaluates each repetition.
- §18 Q1–Q3 were adopted as the RFC recommended (D20–D22), so §18 is empty; each is the maintainer's to reopen.
- The CRAN-mode suite takes 7.9 s locally (budget 15 s); the heavy properties and the two-process test skip there.
- A stuck `apt-get` held the hardening canary for an hour; its jobs now have timeouts (15 and 30 minutes) and apt a two-minute dpkg lock wait.

## Acceptance criteria against stages

| § 19 | Criterion | Stage |
|---|---|---|
| 1 | builds everywhere with zufast from CRAN, `jsonlite` the only runtime import | 0, 6 |
| 2 | the boundary fixture reproduces on every platform | 1 |
| 3 | block independence by property and fuzzer | 1 |
| 4 | Python `fastcdc` agrees | 5 |
| 5 | atomic or idempotent store operations under two processes | 3, 4 |
| 6 | corrupt chunk and bad manifest refused | 2, 3 |
| 7 | clean check; only `R_init_zudedup` exported | 0, 6 |

## Explicitly not in 0.1.0

Compression at rest · manifest files unless §18 Q2 admits them · delta encoding · a Merkle tree · remote backends (the interface ships; implementations do not) · a C API.

## Risk register

| Risk | Stage | Mitigation |
|---|---|---|
| a format constant changes after a store exists | 0 | the table, masks and fixture are committed before any chunking code; `test-boundaries.R` is a permanent regression |
| the Python `fastcdc` comparison cannot substitute the table | 5 | its table is a module constant; if that changes, pin the Python version the job installs |
| zufast's CRAN release slips | 6 | every other stage proceeds |
| `rename()` is not atomic on a platform or filesystem | 3 | the two-process test runs on all three platforms; document the filesystems where it is not |
| a user passes `dedup_gc()` an incomplete `keep` | 4 | the documentation says so in its first paragraph; nothing else can be done |
| XXH3 collision in a shared store | all | documented as non-cryptographic everywhere the default is named; `sha256` one argument away |

## After 0.1.0

1. dastash's adoption and whatever it shows the backend interface gets wrong.
2. §18 Q1 and Q2 as their triggers arrive; `zujson` for the metadata file when it is on CRAN (D9).
3. A Merkle tree over manifests if partial verification is asked for.
